## 这份台账凭什么可信

台账不是散文，是**闸口的数据源**：`scripts/verify_content_ledger.py` 逐行机检，任何一条不成立都红。

| 判据 | 含义 |
|---|---|
| C1 覆盖面 | `git diff --diff-filter=DR --name-only <基线> HEAD` 的每个路径都在本表出现——少一条即红 |
| C2 无幽灵行 | 本表出现的每个原路径都必须真的被删除或改名过——写一行仓库里没发生过的路径即红 |
| C3 去向可达 | 去向列的每个 `路径` 必须真实存在；每个 「「小节」」 必须在目标册内**恰好命中一个标题** |
| C4 改名一致 | 处置为「改名」的行，去向必须等于 `git diff -M` 实测的改名目标 |
| C5 判据非空 | 每行判据必须给出承接证据或明确的废弃理由，不得留空 |
| C6 基线可指认 | 基线 tag 写死在脚本里，tag 不存在即 fail closed（不静默跳过）；并断言该 tag 的 `references/` 树与 `v9.19.2` 逐字相同 |

**基线**：`baseline/v9.19.2-pre-redo` → `725e852`（重做前 `master` 的最后一态）。
其 `references/` 树与 `v9.19.2` = `e30864c` 逐字相同（C6 断言），所以两个 tag 无论指哪个，本表都成立。
选 `725e852` 而不直接改用 `v9.19.2`：`docs/research/ltw-baseline/BASELINE.md`、
`docs/final-integration-report.md`、`diff-baseline.py` 的 `--tag` 默认值与 `baseline-manifest.tsv`（164 行）
四处都把 `baseline/v9.19.2-pre-redo` 定义为 `725e852`——只补 tag、不改这四处记载，四处同时变真。

**处置四类**：「删除」= 内容并入别册、原文件不再存在；「改名」= 同一册换路径；
「拆分」= 同一旧册的内容分到两册以上；多册并成一册的登记为「删除」，去向写合并后的册。

**去向按旧册小节逐段定位**，不是给整册挑一个「最像」的落点：多节落到不同册时每一处都列出
（`references/data/curriculum.md` 即 6 处落点：4 处落 planning、2 处落 intake-optional）。
判据列给每处落点的逐字命中行数。**逐字比对是下限，不是内容保真的全部证据**：它只证明
「这 M 行还在」，证明不了「其余行没丢」——后者由人读与 code review 承担，本表不假装机检能覆盖它。

复测（只读，需要完整 git 历史）：

```bash
python -B scripts/verify_content_ledger.py             # 机检本表
python -B scripts/verify_content_ledger.py --selftest  # 机检 + 12 个自测用例
git diff --diff-filter=DR --name-status -M baseline/v9.19.2-pre-redo HEAD   # 本表所依据的原始清单
```
