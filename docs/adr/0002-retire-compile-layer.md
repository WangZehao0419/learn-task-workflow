# ADR-0002：编译层按职责拆分退役（含保留加载器的 P0 修正）

- 状态：已采纳
- 日期：2026-11-08
- 决策者：维护者
- 相关：规格 #19；ADR-0001

## 背景

仓库里有一套自研编译层：

- `contracts/rules.json`（4742 行）：`files`（127 条文件清单）、`rules`（74 条规则编号登记）、
  `scenes`（21 个场景注册表）、`intents`（45 条跨文件意图登记）、`retired_rule_ids`
- `scripts/rule_contract.py`（1978 行）：拓扑检查、场景覆盖、意图指针闭合、派生表生成与校验
- `SKILL.md` 里由脚本生成的三张表：加载场景表、场景叠加表、补读表

它服务的目标是**索引自洽**，不是学员体验。而它带来的成本是实打实的：
改一条教学规则要先改契约、再跑生成器、再校验一百余个分册的头与指针。

## 决策

**按职责拆分退役，不按名字整体删除。**

### 为什么必须按职责拆

**P0 修正**：契约校验器 `rule_contract.py` **同时是七个确定性脚本的运行时常量加载器**。
`progress_check.py` / `task_index.py` / `scheduler.py` / `ltw_parse.py` / `verify_explanation.py`
都在 import 期执行 `rule_contract.load_or_exit()["constants"]`。
**按名字整体删掉这个模块，七个脚本会当场 KeyError / ImportError。**

所以退役的是**职责**，不是文件：

| 退役 | 保留 |
|---|---|
| 场景注册表、意图登记、文件清单、规则编号登记、退役编号表 | 结构版本（schema / version） |
| 拓扑/覆盖/审计/派生表生成与校验子命令 | 业务常量加载（枚举、阈值、判分四态、调度参数） |
| `SKILL.md` 三张派生表 | 一张条件指针表（遇到 Y 就读 X） |

### 常量去留按实际消费判定

实测（探针拦截 `__getitem__`，记录脚本真正读到的键）：

- **保留 17 个顶层键**：phases / types / subject_families / group_slugs / discipline_slugs /
  review_origin_phases / grading / kp / gates / restatement / budget / schemas / headings /
  scheduler / errors / **starts** / **reader**
- **退役 2 个**：`handout`（数值已写在 `references/handout-layout.md` §2.8）、
  `intent_semantics`（全仓零消费）

> `starts` 与 `reader` 差一点被误删：静态扫描只在函数体内找到引用，漏掉了 **import 期读取**。
> 这是 P0 修正的第二个实例——「看起来没人用」和「实际没人用」不是一回事，必须跑一遍才知道。

### 索引机检随编译层退役，不新造闸口

**不保留任何简化版场景表**，也不把索引校验改造成别的东西。兜底改用：

- 逐文件差异比对（内容保真校验，仓库外维护侧工具）
- 七个脚本的 import 不变量（`--selftest` 全绿即证明常量加载路径没断）
- 行为机检（讲义/标记/可读性/公式/加载足迹结构）

## 后果

- **正面**：改一条规则只需改一处；契约 4742 行 → 357 行，加载器 1978 行 → 纯常量加载器。
- **正面**：结构改动不再被一堆自洽性闸口绑住。
- **负面**：失去「契约与文档逐字一致」的机器保证。改用**写作纪律**（一个概念只在一处出现）
  加内容保真比对兜底——比机检弱，但机检本身没改善过任何学员体验。
- **风险**：内容保真校验器是维护侧工具、不入库，它自己也可能出错。
  已用可证伪自测（注入删除/注入新增必须被抓到）约束它。
